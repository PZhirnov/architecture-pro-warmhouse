### Общие сведения о компании

«Тёплый дом» — это небольшая компания, которая организует удалённое управление отоплением в доме. Недавно она выиграла тендер и получила заказ на создание экосистемы умных посёлков на территории нескольких регионов страны.

Для выполнения заказа компании нужно расширить функционал своей системы и масштабировать её. ==🔴Пользователи должны иметь возможность управлять не только отоплением, но и умными устройствами в доме==. Чтобы подключиться к экосистеме, в домах должны быть установлены специальные датчики и реле. Сейчас они есть только в половине домов, которые хотят подключиться.

Состояние компании в настоящий момент ==🔴не позволяет в полной мере реализовать новые бизнес-цели==. Для этого требуется пересмотр и оптимизация всей экосистемы.

#### 3.3. Ограниченные контексты

##### 1) Cценарии автоматизации
- **Ответственность:** создание, валидация и исполнение правил автоматизации; реакция на события устройств.
- **Ключевые понятия:** `Правило`, `Событие`, `Условие`, `Действие`
- **Агрегаты:** Правила автоматизации, Сценарии.
- **Доменные события (входящие):** Получение сообщения/запроса, Изменение состояния датчика
- **Доменные события (исходящие):** Сработало правило/контроль (правило начало работу), Запросы на выполнения действий датчиком (включи свет, уменьши температуру и т.д.), .
##### 2) Управление устройствами (Supporting Subdomains )
- **Ответственность:** регистрация и сопряжение устройств, хранение сведений об устройствах (наименование, тип, измеряемые единицы ), управление состоянием, отправка команд на устройство, отслеживание «в сети / не в сети» (online/offline).
- **Ключевые понятия:** `Device` (устройство), `DeviceType` (тип устройства), `DeviceState` (состояние устройства), `Command` (команда), `PairingSession` (сеанс сопряжения).
- **Агрегаты:** `Device` (корневой агрегат), `PairingSession` (сеанс сопряжения).
- **Доменные события:** `DeviceRegistered` (устройство зарегистрировано), `DevicePaired` (устройство сопряжено с домом), `DeviceWentOffline` (устройство ушло в офлайн), `DeviceStateChanged` (состояние устройства изменилось), `CommandExecuted` (команда выполнена), `CommandFailed` (команда не выполнена).
- **Интеграция:** принимает команды от Automation (движка сценариев) и от пользовательских обработчиков (хендлеров); публикует события для Telemetry (сбора показаний) и Automation (движка сценариев).
##### 3) Телеметрия и мониторинг (Supporting Subdomains )
- **Ответственность:** приём показаний от датчиков, нормализация, хранение временных рядов, агрегации (средние, min/max за период), обнаружение аномалий.
- **Ключевые понятия:** `Reading`, `Sensor`, `TimeSeries`, `Aggregation`, `Anomaly`.
- **Агрегаты:** `Reading` (по сути — append-only событие, event-sourcing-friendly); `SensorStream` как проекция.
- **Доменные события:** `ReadingReceived`, `AnomalyDetected`, `ThresholdExceeded`.
- **Интеграция:** публикует `ReadingReceived` для Automation; читает метаданные устройств из Device Management (через ACL, не напрямую в БД).

##### 4) Локация устройств (Supporting Subdomains )
- **Ответственность:** структура дома, комнаты/зоны, привязка устройств к помещениям, геолокация дома.
- **Ключевые понятия:** `Home`, `Room`, `Zone`, `Floor`, `GeoLocation`.
- **Агрегаты:** `Home` (корень, содержит `Room`/`Zone` как сущности внутри агрегата).
- **Доменные события:** `HomeCreated`, `RoomAdded`, `DeviceAssignedToRoom`.
- **Интеграция:** Device Management ссылается на `HomeId`/`RoomId`; Access Control — на `HomeId`.

##### 5) Access Control Context (Supporting)

- **Ответственность:** жители дома, роли, права на устройства/зоны, приглашения, отзыв доступа.
- **Ключевые понятия:** `Resident`, `Role`, `Permission`, `Invitation`, `AccessPolicy`.
- **Агрегаты:** `Resident` (корень), `HomeMembership`.
- **Доменные события:** `ResidentInvited`, `ResidentJoined`, `AccessGranted`, `AccessRevoked`.
- **Интеграция:** предоставляет проверку прав для хендлеров других контекстов (через API/ACL).

##### 6) Нотификация (Generic)
- **Ответственность:** доставка оповещений жителям по каналам (push/email/SMS), шаблоны, настройки подписок.
- **Ключевые понятия:** `Notification`, `Channel`, `Template`, `Subscription`.
- **Интеграция:** подписывается на события других контекстов (`AnomalyDetected`, `DeviceWentOffline`, `RuleFailed`); не содержит бизнес-логики дома.

##### 7) Аутентификация (Generic)
- **Ответственность:** аутентификация, токены, MFA, федерация.
- **Интеграция:** все контексты доверяют токенам, выданным здесь. Обычно — внешний провайдер (Keycloak/Auth0).

##### 8) Адаптеры протоколов (Generic)
- **Ответственность:** адаптеры под протоколы (MQTT, Zigbee, Z-Wave, Matter), трансляция внешних сообщений в доменные события Device Management.
- **Ключевые понятия:** `ProtocolAdapter`, `Gateway`, `RawMessage`.
- **Роль:** **Anti-Corruption Layer** между внешним миром и доменом. Device Management не знает о протоколах — только о нормализованных командах и событиях.
- Интеграция:
*Тонкий, но критичный ACL-слой**: он принимает сырые протокольные сообщения от шлюзов, переводит их в нормализованные доменные события через `DeviceMapping`, отдаёт Device Management, а в обратную сторону транслирует доменные команды в протокольные вызовы. Он не хранит бизнес-состояние и не принимает бизнес-решений — его единственная задача — **изолировать домен от изменчивости протоколов**, чтобы добавление нового протокола (Thread, Wi-Fi, proprietary) не затрагивало ни Device Management, ни Automation, ни Telemetry.

### **4. Проблемы монолитного решения**

- Границы контекста не определены, что приводит к некорректному использованию сущностей БД при реализации бизнес-логики приложения 
- Каждый поддомен имеет свой профиль нагрузки, поэтому будут сложности при масштабировании сервиса. Если не учесть особенности выделения ресурсов под отдельные модули, то приложение в целом может падать и не выполнять свои функции.  

Пример: 
Падение монолита из-за модуля Telemetry останавливает **всё**: устройства не получают команды, автоматизация не работает, жители не получают уведомления.
- Будут постоянные проблему при деплое и нарушения релизного цикла
- Одна кодовая база и общие зависимости затрагивают все контексты при обслуживании системы. 
- Одна БД на все контексты, что ограничивает возможности использования разных моделей хранения данных
- Адаптеры и логика преобразования данных в одном месте, что усложняет возможности масштабирования системы

```
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```
